Drone connection prototype PROTOTYPE, throwaway

For issue #22. Opens by double-click, nothing to install.

The question. The Python command bridge talks to the swarm through a drone connection. The bridge sends position targets, takeoff, land, and stop. The drone connection reports, per drone, the flight state, link, position with its measurement time, ranges, battery voltage, and the defensive-hover flag. Before we write the Python interface and its contract suite, does this set of commands and reports hold up? Which commands should be legal in each flight state, and what should the drone connection report when the link or tracking drops?

The mock moves each drone straight toward its target at a placeholder speed limit of 0.5 m/s. Time only moves when you press an "advance time" button, so every run is repeatable. Flight states and field names follow protocol/README.md.

Open items this prototype does not model

  • Reconnect lockout (hardware team). When an old radio connection stays half-open, can a new connection to the same drone get through, or is it locked out until the old one times out? The prototype treats "Restore link" as instant.
  • Bridge process stops (hardware team). When the Python command bridge dies, setpoints stop. The Crazyflie firmware has its own setpoint timeout (CONTEXT.md, Bitcraze commander note), but what the drones do and how fast is not settled. The prototype has no way to stop the bridge.
  • Decided 2026-10-20. The bridge sends targets only to flying drones. Land is allowed while stopped. During defensive hover the drone holds only while the straight line to its target points at the obstacle.
  • Decided 2026-10-20: two timestamps per drone report. The drone connection stamps readings with the flight host clock. Position carries its own measurement time. Ranges, battery, and the defensive-hover flag share one radio measurement time. The hardware team confirms that these three arrive together.
